# 2단계 점검 기록: 설정 저장소와 설정 화면

> 이 기록을 쓴 뒤 **발송 모드(dry_run) 설정을 없앴다**(사용자 결정, §8). 아래 본문의 해당 언급(도메인 보강의 `validate_delivery_mode`, §4 #4, §6 #3)은 당시 기록이다.

범위: SQLite 저장소와 마이그레이션, 설정 서비스(일반 설정, 비밀 값, 웹훅, 변경 이력, 시작 점검표), 상태 화면과 설정 화면, 인증 없는 화면을 지키는 최소 장치.
진행 순서: 시나리오 정리 → 테스트 작성 → **실패(red) 확인** → 구현 → 통과(green) → 점검.

## 1. 결과 요약

| 항목 | 결과 |
|---|---|
| 테스트 | 594개 통과 (1단계의 453개 + 141개) |
| 커버리지 | 줄 100%, 분기 100% (`src/rss_hub`, 861줄, 분기 188개) |
| 린트/포맷, `mypy --strict`, `vulture` | 모두 통과 |
| 변이 확인 | 구현을 일부러 망가뜨린 변이 12개를 모두 테스트가 잡음(대조군 1개 제외). 처음에 1개가 살아남았고 원인은 아래 §4 |
| BDD 연결 | 140개 중 **33개**를 `.feature` 그대로 실행(이전 24개에서 +9: SET-01, 02, 05, 06, 07, 15, 18, 19, 20) |
| 설치본 확인 | 깨끗한 가상환경에 설치한 패키지를 실제 서버로 띄워서 ① 템플릿이 설치본에 들어 있고 ② 설정을 저장한 뒤 **서버를 껐다 켜도 값이 남고** ③ 다른 출처의 요청은 403, 키와 웹훅 주소는 화면에 나오지 않음을 HTTP로 확인 |

## 2. 만든 것

| 구성 | 내용 |
|---|---|
| `storage/` | `Database`(요청마다 연결, 성공 시 커밋, 실패 시 폐기, WAL, 처음 연결할 때 마이그레이션), `migrations.py`(순서 있는 SQL 목록 + `user_version`) |
| `services/settings.py` | 설정 정의 15개(기본값, 검증), 원자적 저장(하나라도 틀리면 아무것도 저장 안 함), 변경 이력, OpenRouter 키, 웹훅(이름 + 쓰기 전용 주소), 웹훅 역할(기본, 시스템. 당시에는 OTT도 있었으나 주제 알림 도입으로 없어졌다), 시작 점검표 |
| `web/admin.py`, `templates/` | 상태 화면, 설정 화면(스크립트 없음, 모바일 대응, 다크 모드), 현재 접속 주소 제안 |
| `web/security.py` | 다른 사이트에서 온 상태 변경 요청 거부, 보안 헤더 |
| 도메인 보강 | `parse_positive_int`, `parse_percent`, `validate_delivery_mode`, `validate_webhook_name` |

## 3. 점검 체크리스트

항상 포함: 단일 수행 원칙, 유지보수성, 확장성, 데드코드/미사용 변수·함수.

| 영역 | 점검 | 결과 |
|---|---|---|
| 단일 수행 원칙 | 계층 분리 | 규칙(`domain`)은 저장소와 HTTP를 모른다. `SettingsService`는 저장소와 규칙만 안다. 화면 라우트는 서비스만 부른다. 환경 변수를 읽는 코드가 소스에 하나도 없음을 테스트(`test_no_environment_variables`)로 고정했다 |
| 단일 수행 원칙 | 큰 함수 | `SettingsService`가 약 200줄로 일반 설정, 키, 웹훅, 이력을 모두 다룬다. 응집된 "설정" 하나라서 지금은 유지하지만, 3단계에서 기능이 더 붙으면 **웹훅 관리를 별도 서비스로 나누는 것**을 검토한다 |
| 유지보수성 | 설정 추가 | 새 설정은 `SETTING_DEFS`에 한 줄 추가하면 폼, 검증, 기본값, 이력이 함께 생긴다(템플릿은 그룹 정의만 고친다) |
| 확장성 | 저장소 교체 | `Database`와 `SettingsService`가 `Clock`, `Database`를 주입받아서 테스트가 임시 파일과 가짜 시계를 쓴다 |
| 데드코드 | 미사용 코드 | 작성 중 넣었던 쓸모없는 `format_time` 함수를 직접 찾아서 삭제했다. 변이 확인으로 불필요한 `rollback()` 호출도 찾아서 삭제했다. 그 뒤 `vulture` 통과 |
| 안정성 | 동시 사용 | 여러 스레드가 처음 접속해도 마이그레이션은 한 번만 실행된다(테스트). 설정은 매번 저장소에서 읽어서 다른 인스턴스의 변경이 재시작 없이 보인다(테스트) |
| 안정성 | 원자성 | 검증 실패가 하나라도 있으면 아무것도 저장하지 않는다(테스트). 오류가 나면 DB 변경을 폐기한다(테스트와 변이 확인) |
| 보안 | 비밀 값 | 키와 웹훅 주소는 `secrets` 표에만 있고 화면, 이력, 스냅샷, 로그, 오류 메시지에 나오지 않는다(테스트). 웹훅은 Discord 호스트만 허용한다 |
| 보안 | CSRF | 상태 변경 라우트 4개와 설정 저장 모두 다른 출처 요청을 거부한다(테스트, 변이 확인). `Origin`, `Sec-Fetch-Site`, 프록시의 `X-Forwarded-Host`를 처리한다 |
| 보안 | 응답 | CSP(`default-src 'none'`), `frame-ancestors 'none'`, `no-store` 등. 화면에 스크립트가 없다. 템플릿은 자동 이스케이프(웹훅 이름에 `<script>`를 넣는 테스트) |
| 보안 | 접근 제어 | **없다(사용자 결정).** 주소를 아는 사람이 직접 접속해서 설정을 바꾸는 것은 막지 못한다 |
| 화면 | 입력 오류 | 오류 메시지는 입력 값을 되돌려 주지 않는다(웹훅 주소). 삭제는 확인란이 필요하다 |

## 4. 이번 단계에서 발견하고 고친 것

| # | 내용 | 조치 |
|---|---|---|
| 1 | 시나리오 SET-01, SET-02, SET-07이 아직 없는 "작업"과 "피드/카테고리"를 검증하도록 쓰여 있었다 | 지금 검증할 수 있는 부분(상태 화면, 역할 지정)과 나중에 연결할 부분(SET-21 신규, SET-07의 피드·카테고리 부분은 M2)으로 나눴다. 존재하지 않는 동작을 검증하는 척하는 테스트를 만들지 않으려는 것이다 |
| 2 | 변이 확인에서 "오류 때 `rollback()` 제거"가 살아남았다 | 테스트 구멍이 아니라 **불필요한 코드**였다. 커밋하지 않고 연결을 닫으면 SQLite가 변경을 버리기 때문이다. 코드를 지우고, 대신 "오류 때도 커밋하도록" 망가뜨린 변이를 새로 만들어서 잡히는 것을 확인했다 |
| 3 | 인증이 없는 화면은 다른 사이트가 사용자의 브라우저로 설정을 바꿀 수 있다 | 시나리오 SET-19, SET-20을 추가하고 구현했다 |
| 4 | 발송 모드 기본값이 live면, 웹훅을 채우는 순간 의도하지 않은 발송이 나갈 수 있다 | 기본값을 **dry_run**으로 바꿨다(설계 §10, §12 #15) |
| 5 | FastAPI가 `HTMLResponse | RedirectResponse` 반환 타입을 응답 모델로 해석하지 못해 오류 | 반환 타입을 `Response`로 바꿨다 |
| 6 | 서버 응답 헤더 확인 스크립트가 처음에 "헤더 없음"으로 나왔다 | 서버가 헤더 이름을 소문자로 보내는데 확인 스크립트가 대소문자를 구분한 탓이었고, 대소문자 구분 없이 다시 확인해서 헤더가 모두 붙어 있음을 확인했다 |

## 5. 스택 변경 (확인 필요)

처음 제안한 **SQLAlchemy 2 + Alembic을 쓰지 않고** `sqlite3` 표준 라이브러리와 직접 쓴 SQL, `user_version` 기반 마이그레이션 러너로 구현했다. 이유와 되돌리는 방법은 설계 문서 §15에 적었다. 마음에 들지 않으면 알려 달라. 표가 늘어나기 전인 지금이 바꾸기 가장 싸다.

## 8. 이후 변경: 발송 모드(dry_run) 제거

사용자 결정으로 **live만 구현**한다. 모드 스위치와 관련된 것을 모두 걷어냈다.

| 구분 | 제거한 것 |
|---|---|
| 코드 | `delivery_mode` 설정, `validate_delivery_mode`, 설정 화면의 선택칸, 상태 화면의 발송 모드 표시 |
| 시나리오 | DLV-18(dry-run), SET-16, SET-17(live 전환 시 대기 글 처리 선택), SET-03 표의 발송 모드 행. 시나리오는 140개 → **137개** |
| 설계 | 전환 절차의 dry-run 단계, `deliveries.status`의 `dry_run` 값, 설계 §12 #15 |

**대신 병행 확인 방법을 바꿨다**: 시험용 Discord 채널의 웹훅으로 먼저 돌려 보고, 확인이 끝나면 웹훅을 운영 채널로 교체한다(설계 §11). 웹훅이 하나도 지정되지 않으면 아무것도 보내지 않는다(DLV-15). 이렇게 하면 모드 스위치가 없어도 운영 채널에 같은 알림이 두 번 올라가는 일을 피할 수 있다.

**결과**: 테스트 588개 통과, 커버리지 100%, `ruff`, `mypy --strict`, `vulture` 통과. 린트가 상태 화면에서 더 이상 쓰이지 않게 된 `snapshot` 변수를 바로 찾아냈고 삭제했다.
