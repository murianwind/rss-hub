# 점검 기록: 사용 피드백 6차

사용자 요청: (1) 모델 잔여 사용량이 "674/700"으로 나오는데 "남은 호출 수/1000"이어야 하지 않나(이전 스파이크에서는 제대로 나왔다), (2) 삭제할 때 체크박스를 없애고 확인 창으로, (3) 피드를 수정할 때도 등록처럼 정상적인 피드인지 검사, (4) RSS 피드, 카테고리, 주제를 한 화면에서 보고 RSS 피드가 길면 안에서 스크롤, (5) 카테고리에 등록한 사이트는 카테고리에만 표시, (6) RSS가 없는 사이트(comscore 블로그)를 구독할 방법.

## 3. 설계 결정(확인이 필요하면 알려 주세요)

| # | 결정 |
|---|---|
| 1 | 삭제 요청은 서버에서도 `confirm=yes` 값이 없으면 거부한다(숨은 값). 확인은 브라우저의 확인 창이 맡고, 서버의 값은 주소를 직접 두드린 실수를 막는 용도다 |
| 2 | 서버가 사용량을 알려 주지 않을 때(키 오류, 네트워크)는 내부 상한 기준("674/700" 모양)으로 보여 준다. 이때만 분모가 700이다 |
| 3 | 세 구역의 기본 열림 상태는 모두 접힘(5차 이전 요청)을 유지했다. 한 화면에 보이려면 각 구역을 열어야 한다 |
| 4 | 모델 체인 교체 확인("이 체인으로 교체합니다" 체크박스)은 삭제가 아니라서 그대로 두었다 |

## 4. 작업 중 발견하고 고친 것

| # | 내용 | 조치 |
|---|---|---|
| 1 | 알 수 없는 가져오기 실패 사유가 그대로 안내에 들어갔다(`가져오지 못했습니다({사유})`). 사유는 수집기가 정하는 분류 이름이라 현실에서는 주소가 들어가지 않지만, 시험이 방어 부재를 보였다 | 짧은 영숫자 이름일 때만 그대로 보여 주고 아니면 일반 문구 |
| 2 | 사이드바에 삭제 폼이 늘 있게 되어, "이 화면에 주제 버튼이 없다"를 `/topics/ID/` 문자열로 확인하던 시험과 설정 화면의 폼 수를 세던 시험이 깨졌다 | 삭제 폼을 제외하도록 정밀화 |
| 3 | 서버 사용량 캐시를 사전(dict)로 두어 `mypy --strict`가 실패했다 | 타입이 있는 작은 클래스로 교체 |
| 4 | 주소 검사 서비스의 "주소 규칙 위반" 분기가 핸들러가 먼저 걸러서 시험되지 않았다(커버리지 확인) | 서비스를 직접 시험 |

**과정에 대한 정직한 기록**: 화면과 스크립트는 구현을 먼저 하고 시험을 나중에 썼다. 모델 사용량과 주소 검사는 시험을 먼저 쓰고 구현했다. 사이드바의 높이 나눔은 `:has()` 선택자를 쓴다(Chrome 105+, Safari 15.4+). 더 오래된 브라우저에서는 이전처럼 구역이 제각각 늘어난다.

## 5. RSS가 없는 사이트를 구독하는 방법(comscore 블로그)

직접 확인한 것: `https://www.comscore.com/Insights/Blog`는 **화면에 RSS 안내가 없고 이메일 구독("Join our Email List")만 있다.** 글 목록은 서버가 그리는 평범한 HTML이고, 글마다 `/Insights/Blog/글이름` 링크, 제목, 날짜가 있다. (내가 받은 본문에서는 `<link rel="alternate">` 같은 숨은 태그는 보이지 않았다. 피드 주소가 숨어 있을 가능성은 이 확인만으로 배제하지 못한다.)

| 방법 | 설명 | 장단점 |
|---|---|---|
| 사이트가 이메일 구독을 주면 | 메일을 RSS로 바꾸는 서비스(Kill the Newsletter 등)로 받는 주소를 만든다 | 사이트 변경이 필요 없다. 메일이 와야 글이 생기고 본문이 메일 모양이다 |
| RSS-Bridge(직접 도커로 실행) | "CSS 선택자" 또는 "XPath"로 목록 페이지에서 글을 뽑아 피드로 만드는 범용 변환기가 있다 | 이미 Portainer를 쓰고 있어서 붙이기 쉽다. 선택자를 직접 지정해야 한다 |
| 호스팅 서비스(rss.app, Feedity, FetchRSS 등) | 페이지 주소를 넣으면 피드를 만들어 준다 | 쉽지만 무료는 제한이 있고 외부에 의존한다 |
| 이 서비스에 "웹페이지 구독" 추가(제안) | 목록 페이지 주소만 넣으면 같은 경로(`/Insights/Blog/…`)의 링크를 글로 보고, 제목과 날짜를 뽑아 일반 피드처럼 수집한다. 선택자 지정은 선택 사항 | 별도 서비스 없이 한 곳에서 관리된다. 사이트 구조가 바뀌면 깨질 수 있고, 만드는 데 작업이 든다 |

이 서비스에 "웹페이지 구독"을 넣을지는 결정이 필요하다(이번에는 만들지 않았다).

## 6. 알려진 한계

| # | 내용 |
|---|---|
| 1 | 서버 사용량 조회는 사이드바를 그릴 때 동기로 호출한다(1분에 한 번). 서버가 아주 느리면 그 한 번의 화면이 느려질 수 있다 |
| 2 | 삭제 확인 창은 브라우저 기본 창이다. 스크립트가 없으면 확인 창이 뜨지 않고 바로 삭제된다(이 서비스는 스크립트가 없으면 대부분의 화면이 동작하지 않는다) |
| 3 | 사이드바의 높이 비율(RSS 42%, 카테고리 33%, 주제 25% 등)은 고정값이다. 화면이 아주 낮으면 각 목록의 최소 높이(90~110px) 때문에 사이드바 전체가 스크롤된다 |
| 4 | Docker 이미지는 이 환경에서 직접 빌드하지 못했다 |
