## 3. 바뀐 것

| 구성 | 내용 |
|---|---|
| `domain/keywords.py` | `ott.py`를 일반화. 일치한 키워드 목록을 돌려준다 |
| `domain/topics.py` | 주제 입력 규칙, `match_topic`(LLM이 골랐고 키워드가 있어야 해당) |
| `domain/routing.py` | 카테고리 웹훅(없으면 기본) + 해당 주제들의 서로 다른 웹훅, 같은 웹훅은 한 번만 |
| `domain/validation.py`, `prompts.py` | 요약 응답에 `topics`(요청한 번호만 인정), 프롬프트에 켜진 주제의 번호와 설명 |
| `storage` | 마이그레이션 6(주제, 글이 해당한 주제, `articles.llm_topics`), 주제 저장소, 카테고리 목록과 웹훅 지정 |
| `services` | 요약은 켜진 주제를 요청에 넣고, 발송은 발송 직전에 주제를 판별해서 기록하고 라우팅 |
| `web` | `/topics`, `/categories`, 설정의 웹훅 역할은 기본과 시스템, 가져오기에서 피드별 웹훅 선택 삭제 |

## 4. 이번 단계에서 발견하고 고친 것

| # | 내용 | 조치 |
|---|---|---|
| 1 | **기본 주제를 앱을 만들 때 DB에 심었다.** `/healthz`가 데이터 폴더에 파일을 만들면 안 된다는 기존 테스트 2개가 이를 잡아냈다. 제 구현이 틀린 것이다 | 서버가 실제로 시작할 때(lifespan)로 옮겼다. 앱을 만드는 것만으로는 디스크를 건드리지 않는다는 테스트와, 시작에 실패해도 서버가 응답하고 로그를 남긴다는 테스트를 추가 |
| 2 | 시나리오 문장에서 조사가 어긋나서 단계를 찾지 못한 것이 두 곳(`와/과`, `이/가`) | 시나리오와 단계 문장을 맞춤 |
| 3 | 옛 시나리오 DLV-15에 "ready 글이 있다"는 단계가 빠져 있던 것처럼, 이번에는 DLV-22가 글을 만들지 않고 발송을 실행했다 | 글을 만드는 단계를 시나리오에 넣음 |
| 4 | 일괄 치환 도중 `ott_id` 인자를 지우는 정규식이 테스트 파일 한 곳에서 다른 줄을 건드릴 뻔했다 | 치환 결과를 출력으로 확인하고 해당 테스트를 직접 고쳤다 |
| 5 | 문서 갱신 확인 출력이 `cut`으로 한글을 잘라서 깨졌다(내용 문제는 아니었다) | 파이썬으로 다시 확인 |

**과정에 대한 정직한 기록**: 새 화면(`/topics`, `/categories`)과 그 테스트는 구현을 먼저 쓰고 테스트를 나중에 썼다(실패를 먼저 확인하지 못했다). 변이 확인으로 보완했다.

## 5. 점검 체크리스트

항상 포함: 단일 수행 원칙, 유지보수성, 확장성, 데드코드/미사용 변수·함수.

| 영역 | 점검 | 결과 |
|---|---|---|
| 단일 수행 원칙 | 계층 | 판별, 라우팅, 입력 규칙은 순수 함수, 저장은 저장소, 요약과 발송 서비스가 연결한다 |
| 유지보수성 | 규칙의 위치 | "LLM 확인 + 키워드" 규칙이 `match_topic` 한 곳에 있다. 키워드 보완 방식을 바꾸려면 그 함수만 고친다 |
| 확장성 | 새 주제 | 코드를 고치지 않고 화면에서 추가한다. OTT 외 주제도 같은 구조다 |
| 확장성 | 판별 기록 | 해당한 주제와 일치한 키워드를 `article_topics`에 남겨서 M5의 피드백과 키워드 개선 제안에 쓸 수 있다 |
| 데드코드 | 미사용 코드 | `vulture` 통과. `ott.py`와 `is_ott_article`, `Purpose`, 피드의 웹훅과 OTT 옵션 코드를 모두 삭제했다 |
| 안정성 | 응답 검증 | 요청하지 않은 번호, 참/거짓, 실수, 중복을 걸러낸다. 주제 항목이 없어도 요약은 채택한다 |
| 안정성 | 설정 변경 | 주제는 발송 직전에 읽는다. 요약 뒤에 주제를 껐다면 그 주제로는 보내지 않는다 |
| 보안 | 화면 | 주제와 카테고리 입력은 이스케이프되고, 상태를 바꾸는 요청은 교차 사이트에서 거부되며 GET을 받지 않는다 |

## 6. 설계 결정(확인이 필요하면 알려 주세요)

| # | 결정 |
|---|---|
| 1 | "LLM 확인 + 키워드 보완"을 **AND**(LLM이 골랐고 키워드도 있어야 해당)로 해석했다. 키워드가 LLM이 놓친 글을 건지는 OR 방식이 의도라면 `match_topic` 한 곳을 바꾸면 된다 |
| 2 | 키워드를 등록하지 않은 주제는 LLM의 판단만으로 정한다 |
| 3 | 주제는 모든 피드에 적용된다. 피드마다 OTT 판정을 끄던 기능은 없어졌고, 카테고리별 적용 범위는 M2 |
| 4 | 기본 주제 OTT의 웹훅은 이전 설정의 OTT 웹훅이 있고 아직 존재하면 그것을 물려받는다 |
| 5 | 주제는 20개까지(요청 프롬프트 길이를 제한) |

## 7. 알려진 한계

| # | 내용 |
|---|---|
| 1 | **새 요약 프롬프트는 실제 무료 모델로 시험하지 못했다.** 스파이크 S1은 옛 `is_ott` 프롬프트로 했다. 가짜 서버로 동작은 확인했지만 모델이 주제 번호를 제대로 내놓는지는 실제 호출로 확인해야 한다 |
| 2 | 키워드 없이 LLM만으로 정하는 주제는 LLM이 근거 없이 고르는 경우를 걸러 주지 못한다 |
| 3 | `feeds.webhook_id`, `feeds.ott_check`, `articles.is_ott` 열은 외래 키 때문에 지우지 못하고 남겨 두었다(쓰지 않는다) |
| 4 | 피드를 카테고리에 넣는 화면은 아직 없다(M2). OPML 폴더로 가져온 카테고리만 만들어진다 |
| 5 | 주제의 키워드 편집은 쉼표나 줄바꿈 입력이다. 키워드별 일치 통계 화면은 없다(M5) |
| 6 | 발송 서비스와 요약 서비스는 아직 주기적으로 실행되지 않는다(7단계) |
