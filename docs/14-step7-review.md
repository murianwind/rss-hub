# 7단계 점검 기록: 알림 규칙 변경과 잡 연결

범위: ① 알림 규칙 변경(피드 웹훅 복구, 카테고리와 상호 배제, 기본 웹훅에서 빠지는 규칙) ② 잡 연결(수집, 요약, 발송), `/healthz` 정체 판정, `/status`, `/a/{id}`, 종료 처리, Docker 시작 명령.
사용자 결정(2026-10-17): 주제 글이 기본 웹훅에서 빠진 피드에서 기본 웹훅으로 가는지는 **B안**(가지 않는다), 피드 웹훅은 카테고리에서 빠지면 다시 지정 가능, "주제로" 버튼은 소급 발송하지 않는다.

## 2. 알림 규칙 변경

| 구성 | 내용 |
|---|---|
| `domain/routing.py` | 피드 웹훅 → 카테고리 웹훅 → 기본 웹훅 중 첫 지정값 하나 + 해당 주제들의 서로 다른 웹훅 |
| `storage/feeds.py` | `set_feed_webhook`, `set_feed_category`, 상호 배제 규칙(카테고리 소속 피드는 웹훅 불가, 웹훅이 있는 피드는 카테고리 불가). 어기면 `FeedRuleError`(화면에 그대로 보여 줄 수 있는 메시지) |
| `web/feeds.py` | `/feeds` 화면: 피드별 카테고리와 웹훅 지정. 카테고리에 속한 피드는 웹훅 선택 대신 카테고리의 설정을 따른다는 안내 |

B안의 결과: 카테고리나 피드 웹훅으로 가는 피드의 OTT 글은 그 웹훅과 OTT 웹훅으로만 가고 기본 웹훅에는 가지 않는다. 기본으로 가는 피드의 OTT 글은 기본과 OTT 웹훅으로 간다.

## 3. 잡 연결

| 구성 | 내용 |
|---|---|
| `domain/jobs.py` | 슬롯 시각 계산, 지나간 슬롯은 따라잡지 않음(유예 60초), 간격 작업 판단 |
| `storage/job_runs.py`(마이그레이션 7) | 작업마다 한 줄: 시작, 종료, 마지막 성공, 오류 종류, 건너뜀 횟수 |
| `jobs/runner.py` | 수집은 5분 슬롯, 요약과 발송은 간격으로 실행. 같은 작업이 실행 중이면 건너뛰고 기록(같은 시점은 한 번만). 주기는 매번 설정에서 읽어서 재시작 없이 반영. 실패는 예외 종류만 기록. 종료 시 진행 중인 작업을 기다림 |
| `runtime.py`, `main.py` | 실제 어댑터로 서비스를 조립. 서비스 시작점은 `rss_hub.main:create_service_app`(Dockerfile의 시작 명령도 바꿨다) |
| `services/deliver.py` | 종료 신호가 오면 지금 글의 모든 목적지까지 마치고 나머지는 `ready`로 남긴다 |
| `web/app.py` | 서버 시작 때 실행기를 시작, 종료 때 최대 30초 기다리며 멈춤. `/healthz`: 수집이 15분(수집 주기의 3배와 15분 중 큰 값) 넘게 멈추면 503 `stale`. 방금 시작해서 아직 수집한 적 없으면 시작 시각을 기준으로 한다 |
| `web/admin.py`, `status.html` | `/status`(`/`와 같은 화면): 발송 대기 글, 요약 대기 글, 오늘 LLM 호출, 실패 피드, 작업별 마지막 성공과 건너뜀 |
| `web/articles.py` | `/a/{id}`: 원문으로 302 이동. http, https가 아니거나 제어 문자가 든 주소, 없는 글은 404 |

## 4. 이번 단계에서 발견하고 고친 것

| # | 내용 | 조치 |
|---|---|---|
| 1 | **조립한 실행기 테스트 3개가 처음에 실패했다.** 원인은 코드가 아니라 내 가정이었다. 수집은 슬롯마다 실행되지만 우선순위가 보통인 피드는 한 시간에 한 번(자기 슬롯)만 점검된다(기존 설계). 5분 뒤에는 새 글을 가져오지 않았다 | 직접 돌려서 확인한 뒤, 테스트를 "매 슬롯 점검" 피드로 바꾸고 보통 피드가 한 시간에 한 번만 점검된다는 테스트를 추가했다 |
| 2 | **변이 확인에서 살아남은 것**: 서비스 시간대를 무시하고 UTC로 슬롯을 계산해도 테스트가 통과했다. 한국(+9:00)은 UTC와 분이 같아서 차이가 안 났다 | 분이 어긋나는 시간대(인도 +5:30)로 검증하는 테스트 추가 |
| 3 | `app.py` 수정 스크립트가 중간에 멈춰서 적용되지 않았고, 이미 바뀐 관리 라우터와 호출부가 어긋나 테스트 130개가 오류를 냈다 | 포맷터가 바꿔 놓은 현재 코드 모양을 확인하고 다시 적용했다 |
| 4 | 시나리오 SVC-03, 04가 `/status`를 요구하는데 상태 화면을 `/`에만 만들어 두었다 | `/status` 별칭을 추가하고 두 경로가 같은 화면임을 검증 |
| 5 | 시나리오의 조사가 `을`과 `를`로 섞여 있는데 내 단계 정의는 `을`만 받았다 | 둘 다 받도록 수정 |
| 6 | 내 테스트에 아무 효과 없는 `monkeypatch`가 하나 남아 있었다(기본 인자는 함수 정의 때 정해져서 바꿔도 소용없다) | 삭제 |
| 7 | 내가 쓴 `ruff format`이 줄바꿈을 바꿔서, 직후에 쓴 문자열 치환이 두 번 맞지 않았다 | 현재 모양을 확인하고 맞춰서 적용 |

**과정에 대한 정직한 기록**: `/feeds` 화면과 `/status` 확장, `/a/{id}`는 구현을 먼저 쓰고 테스트를 나중에 썼다(실패를 먼저 확인하지 못했다). 변이 확인으로 보완했다.

## 5. 점검 체크리스트

항상 포함: 단일 수행 원칙, 유지보수성, 확장성, 데드코드/미사용 변수·함수.

| 영역 | 점검 | 결과 |
|---|---|---|
| 단일 수행 원칙 | 시각 규칙, 실행, 조립 | 시각 계산은 순수 함수(`domain/jobs`), 실행과 겹침 방지는 `JobRunner`, 부품 조립은 `runtime`에 둔다. 서비스(수집, 요약, 발송)는 실행기를 모른다 |
| 유지보수성 | 설정 반영 | 주기, 시간대, 모델 체인, 서비스 주소는 실행할 때마다 설정에서 읽는다. 재시작이 필요 없다(SET-03, 04) |
| 확장성 | 작업 추가 | 작업 하나는 이름 + 실행 함수 + 주기 함수다. 새 작업은 `runtime.py`에 한 줄 추가 |
| 데드코드 | 미사용 코드 | `vulture` 통과(라이브러리가 읽는 속성 이름만 예외 목록에 있다) |
| 안정성 | 겹침과 재시작 | 실행 중인 작업은 건너뛰고 기록한다. 재시작해도 지나간 슬롯을 따라잡지 않는다. 기록은 데이터베이스에 있어서 재시작 뒤에도 이어진다 |
| 안정성 | 종료 | 종료 신호가 오면 새 작업을 시작하지 않고 진행 중인 발송은 지금 글까지 마친다. 실제 스레드로 시험(SVC-10) |
| 안정성 | 한 작업의 실패 | 한 작업이 실패해도 다른 작업은 계속 돈다. 일정 계산 실패와 스케줄러 오류도 로그만 남기고 이어진다 |
| 보안 | 비밀 값 | 작업 실패는 예외 종류만 기록(메시지에 웹훅 주소나 키가 있어도 새지 않음), `/healthz`와 `/status`에 웹훅 주소, 키, 환경 변수 값이 없음(SVC-04) |
| 보안 | `/a/{id}` | `javascript:`, `file:`, `data:`, 빈 호스트, 줄바꿈이 든 주소는 이동하지 않는다 |

## 6. 설계 결정(확인이 필요하면 알려 주세요)

| # | 결정 |
|---|---|
| 1 | 정체 판정 기준은 수집이 `max(15분, 수집 주기의 3배)` 넘게 멈췄을 때다 |
| 2 | 서버를 슬롯이 아닌 시각에 시작하면 첫 수집은 다음 슬롯까지(최대 5분) 기다린다. 슬롯 시작 후 60초 안에만 실행하고 놓친 슬롯은 따라잡지 않기 때문이다(재시작 직후 점검이 몰리지 않게 하는 기존 설계) |
| 3 | "주제로" 버튼을 누른 글을 소급해서 주제 웹훅으로 보내지 않는다(버튼은 아직 없다) |

## 7. 알려진 한계

| # | 내용 |
|---|---|
| 1 | **새 요약 프롬프트는 실제 무료 모델로 시험하지 못했다.** 모델이 주제 번호를 제대로 내놓는지는 실제 호출로 확인해야 한다 |
| 2 | **SET-13(웹훅 시험 전송), SET-14(OpenRouter 키 확인)는 구현하지 않았다.** 설정 화면에 해당 버튼이 없다. 배포 후 병행 확인에서 시험 채널 웹훅으로 직접 확인해야 한다 |
| 3 | 사설망 주소 차단 때문에 집 안의 피드는 수집되지 않는다(사용자 결정) |
| 4 | Docker 이미지를 이 환경에서 직접 빌드하지는 못했다(Docker가 없다). Dockerfile의 시작 명령이 서비스 시작점을 가리키는지는 테스트로 확인했고, 같은 패키지를 가상환경에 설치해서 실제 uvicorn으로 시작하는 것은 확인했다 |
| 5 | 실행기는 단일 프로세스를 전제로 한다. 컨테이너를 두 개 이상 띄우면 같은 작업이 중복 실행된다(compose는 한 개만 정의) |
| 6 | 뷰어(사이드바, 주제 목록), 좋아요/싫어요, "주제로" 버튼, 키워드 개선 제안은 아직 없다(M4, M5) |
| 7 | 서버가 꺼져 있던 동안 올라온 글은 다음 점검에서 "오늘 발행" 기준으로만 가져온다(기존 수집 규칙) |
