# S2 결과: Discord 웹훅

실행: 2026-10-16 09:31(UTC), `tools/spike.py discord`, 시험용 채널과 시험용 웹훅

## 1. 확인한 것

| 항목 | 결과 | 설계에 쓰는 방법 |
|---|---|---|
| `?wait=true`로 보내기 | HTTP 200, 응답에 메시지 객체(`id`, `channel_id`, `content`, `timestamp`, `webhook_id` 등) | 메시지 `id`를 발송 기록에 저장한다 |
| `?wait` 없이 보내기 | HTTP 204, 본문 없음 | 항상 `?wait=true`로 보낸다(id를 얻기 위해) |
| 글자 수 한도 | 1900자와 2000자는 200, **2001자는 400** | 한도는 2000자. 우리 상한 1900자는 여유가 있다 |
| 한도 헤더 | `x-ratelimit-limit: 5`, `x-ratelimit-remaining: 4`, `x-ratelimit-reset-after: 1`, `x-ratelimit-bucket` | 보낸 직후 남은 횟수가 0이면 `reset-after`만큼 기다려서 429를 피한다(최대 10초) |
| 연속 8회 발송 | 모두 200, **429가 나오지 않았다** | 아래 §2 |
| 메시지 삭제 | 11개 모두 204 | 웹훅 주소로 보낸 메시지를 지울 수 있다(지금은 쓰지 않는다) |

## 2. 확인하지 못한 것

| 항목 | 이유 | 지금의 가정 |
|---|---|---|
| 429 응답의 모양 | 연속 8회로는 한도에 걸리지 않았다(한도 5회/약 2초인데 요청이 순차라서 걸리지 않은 것으로 보인다) | 문서대로 `Retry-After` 헤더(초), 없으면 본문의 `retry_after`를 읽는다. 둘 다 없으면 5초 대기. 최대 30초 |
| 400, 404 응답의 본문 | 보고서가 본문을 찍지 못했다. 400 응답이 일반적인 오류 형식이 아니었던 것으로 보인다 | 상태 코드만으로 판단한다. 본문은 읽지 않는다 |
| 삭제된 웹훅으로 보냈을 때의 응답 | 선택 시험이라 하지 않았다 | 404를 "웹훅이 삭제됨"으로 가정한다. 401과 403도 같은 영구 실패로 취급한다 |
| 첫 메시지의 모양(굵은 글씨, 링크) | 사람이 눈으로 확인해야 하는 항목이다 | 확인 결과를 받지 못했다 |

## 3. 설계 반영

- 발송 어댑터는 `?wait=true`로 보내고 응답의 `id`를 기록한다.
- 글자 수는 1900자로 제한한다(이미 `domain/message`에 있다).
- 속도 조절은 429를 받은 뒤가 아니라 **한도 헤더를 보고 미리** 한다.
- 429 형식은 가정으로 구현하고, 실제 429를 받으면 헤더와 본문을 읽는 부분이 맞는지 `docs/10-step5-review.md` §7의 항목으로 남겨 둔다.
