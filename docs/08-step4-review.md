# 4단계 점검 기록: LLM 게이트웨이, 호출 예산, 요약 서비스

범위: OpenRouter 클라이언트(어댑터), LLM 게이트웨이(모델 체인, 재시도, 호출 기록), 호출 예산 가드(하루 상한, 분당 상한, 서버가 알려 준 남은 호출 수), 시스템 알림 서비스, 요약 서비스, 관련 저장소(호출 기록, 알림 기록, 글의 요약 결과), 마이그레이션 3.
호출 방식의 근거는 스파이크 S1 결과(`docs/07-spike-s1-result.md`)다.

## 3. 만든 것

| 구성 | 내용 |
|---|---|
| `domain/budget.py` | 호출을 막아야 하는지 판단(하루 상한, 서버 남은 수, 분당 상한 순), 경고 비율 도달 판단 |
| `domain/prompts.py` | S1에서 검증한 JSON 요청 프롬프트와 본문 발췌(HTML 제거, 앞 1500자) |
| `domain/summary.py` | 처리 순서: 처음 처리하는 글을 먼저, 같은 그룹은 오래된 글부터 |
| `adapters/openrouter_client.py` | 요청 만들기, 응답 해석, 오류 분류(7종류), 모델 옵션 조회(1시간 재사용), 서버 사용량 조회 |
| `services/llm_gateway.py` | 모델 체인, 429 재시도, 옵션 거부 시 재시도와 기억, 계정 수준 문제에서 체인 중단, 호출 기록, 예산 가드, 80% 경고 |
| `services/alerts.py` | 시스템 알림: 쿨다운, 하루 한 번 알림, 보내지 못하면 기록하지 않고 다음에 재시도 |
| `services/summarize.py` | 요약 작업: 검증, 재시도 횟수, 원문 발췌 확정, 장애와 불량 응답의 구분 |
| `storage/` | `llm_usage`, `alert_log` 표(마이그레이션 3), 글의 요약 결과(`mark_ready`, `bump_retry`, `finalize_fallback`) |
| 설정 | `llm_reserve_calls`(서버 남은 호출 예비분, 기본 20) 추가 |

## 4. 이번 단계에서 발견하고 고친 것

| # | 내용 | 조치 |
|---|---|---|
| 1 | **서버가 알려 주는 남은 호출 수를 반영하지 않으면 예산이 어긋난다.** 키 정보에서 `free_model_daily_requests`의 실제 값(`used` 33, `limit` 1000)을 확인했다. 같은 키를 쓰는 기존 크론의 호출은 우리 기록에 없다 | 시나리오 BUD-15~17 추가, 설계 §7-4에 반영. 이 값은 5분 재사용, 조회 실패 시 우리 기록만으로 판단 |
| 2 | 변이 확인에서 살아남은 것 ①: 80% 경고를 "하루 한 번"으로 제한하는 코드를 지워도 테스트가 통과했다. 쿨다운(6시간)만으로도 시험 시간 안에서는 같은 결과였다 | 쿨다운이 지난 뒤에도 같은 UTC 날짜에는 다시 보내지 않는 테스트 추가 |
| 3 | 살아남은 것 ②: 대기 허용 시간이 **정확히 60분**일 때의 동작을 검증하지 않았다 | 59분, 60분, 61분 경계 테스트 추가(60분은 확정) |
| 4 | 살아남은 것 ③: 키는 있지만 기본 웹훅이나 서비스 주소가 없을 때 요약을 멈추는 동작을 검증하지 않았다(키만 검증했다) | 세 설정 각각이 빠졌을 때를 검사하는 테스트 추가(SET-21의 요구) |
| 5 | 살아남은 것 ④는 테스트 구멍이 아니라 내 확인 스크립트가 코드 모양(포맷터가 줄을 바꿈)과 다른 문자열을 찾은 탓이었다 | 실제 코드에서 문자열을 읽어 다시 확인했고 잡힌다 |
| 6 | SUM-07 시나리오에 글을 수집한다는 단계가 빠져 있었다 | 시나리오 수정 |
| 7 | BUD-05, BUD-06이 "호출 1번"을 기대했지만, 모델 체인이 2개이고 429에는 재시도가 있어서 호출 수가 모호했다 | 체인을 모델 하나로 못 박고, BUD-06은 "429 실패 + 재시도 성공 = 12회"로 명확히 했다 |
| 8 | 호출 700건을 기록하는 테스트 도우미가 한 건마다 DB 연결을 열어서 전체 테스트가 44초까지 늘었다 | 도우미만 일괄 삽입으로 바꿔서 17초로 줄였다(운영 코드는 그대로) |
| 9 | `LlmNotConfigured` 경로(키가 실행 도중 사라진 경우)가 테스트로 닿지 않았다 | 게이트웨이가 그 예외를 올리게 만든 테스트 추가 |
| 10 | 설정 테스트의 기대값이 틀렸다(`-1`은 숫자이므로 "숫자만 입력할 수 있음"이 아니라 범위 오류가 맞다) | 테스트 수정 |

**과정에 대한 정직한 기록**: 도메인 규칙 3개(`budget`, `prompts`, `summary`)는 테스트와 구현을 같은 단계에서 썼고 실패를 먼저 확인하지 못했다. 나머지(저장소, 어댑터, 서비스, BDD)는 실패를 먼저 확인했다. 앞의 3개는 변이 확인(경계값 변이 3개 포함)으로 보완했다.

## 5. 점검 체크리스트

항상 포함: 단일 수행 원칙, 유지보수성, 확장성, 데드코드/미사용 변수·함수.

| 영역 | 점검 | 결과 |
|---|---|---|
| 단일 수행 원칙 | 계층 | 판단 규칙(`domain/budget`)은 순수 함수, 호출과 기록은 게이트웨이, 글 상태 전이는 요약 서비스, HTTP는 어댑터가 맡는다. 알림 전송(`Notifier`)과 LLM 호출(`LlmClient`)은 포트라서 서비스가 외부를 직접 모른다 |
| 단일 수행 원칙 | 큰 함수 | `LlmGateway._try_model`이 재시도, 옵션 거부, 계정 문제를 한 반복문에서 처리한다. 분기가 많지만 한 가지 일(모델 하나를 성공 또는 포기할 때까지)이다. 규칙이 더 늘면 재시도 정책을 따로 떼는 것을 검토한다 |
| 유지보수성 | 설정 | 모델 체인, 상한, 경고 비율, 분당 상한, 예비분, 대기 허용 시간, 쿨다운, 요약 묶음은 모두 설정에서 매번 읽는다(재시작 없이 반영, BUD-13, 14) |
| 확장성 | 모델 옵션 | 모델이 지원한다고 알린 옵션(`supported_parameters`)에 따라 요청이 달라진다. 새 모델을 체인에 넣어도 코드를 고치지 않는다. 옵션을 거부하면 빼고 다시 시도하고 기억한다 |
| 확장성 | 알림 종류 | 알림은 종류 이름과 문구만 정하면 쿨다운과 기록이 공통으로 적용된다 |
| 데드코드 | 미사용 코드 | `vulture` 통과 |
| 안정성 | 호출 낭비 방지 | 장애가 확인되면 같은 실행의 나머지 글에는 호출하지 않는다. 계정 수준 문제(402, 401/403, 개인정보 설정)는 체인의 다른 모델을 시도하지 않는다. 하루 상한에 도달하면 서버에 묻지도 않는다 |
| 안정성 | 한도 | 실패한 호출, 재시도, 모델 전환을 모두 한 번으로 센다. 상한은 재시도 전에도 다시 검사한다(마지막 한 번을 429로 쓰면 재시도하지 않는다, 테스트) |
| 안정성 | 장애와 불량 응답 | 장애는 재시도 횟수를 올리지 않는다. 불량 응답만 센다. 장애가 대기 허용 시간(기본 60분)을 넘기면 원문 발췌로 확정한다 |
| 안정성 | 예외 격리 | 글 하나의 예상 못한 예외는 재시도 1회로 세고 나머지를 계속 처리한다 |
| 보안 | 키 | 호출할 때마다 설정에서 읽어서 인증 헤더에만 쓴다. 오류 문구에서 키를 가리고 200자로 자른다(테스트). 로그에 키나 웹훅 주소를 남기지 않는다 |
| 데이터 | 시간 | 호출 기록의 "하루"는 UTC 날짜다. 한국 시간 자정에는 바뀌지 않는다(테스트) |

## 6. 설계 결정(확인이 필요하면 알려 주세요)

| # | 결정 |
|---|---|
| 1 | 서버 남은 호출 예비분 기본값은 **20**이다. 같은 키를 쓰는 다른 프로그램의 몫을 남겨 두는 값이다 |
| 2 | 잔액, 키, 개인정보 설정 문제는 체인을 멈추고 알린다(모든 모델에 똑같이 일어나므로 호출을 낭비하지 않는다) |
| 3 | 분당 상한에 걸려도 알림은 보내지 않는다(잠깐 기다리면 풀린다) |
| 4 | 키, 기본 웹훅, 서비스 주소가 모두 채워지기 전에는 요약하지 않는다(SET-21). 서비스 주소는 요약에 직접 필요하지 않지만 시나리오가 그렇게 요구한다 |
| 5 | 80% 경고만 UTC 하루에 한 번이고, 나머지 알림은 쿨다운(기본 6시간)이다 |

## 7. 알려진 한계

| # | 내용 |
|---|---|
| 1 | **요약 작업은 아직 주기적으로 실행되지 않는다.** 잡 연결은 7단계다 |
| 2 | **시스템 알림을 실제로 보내는 어댑터가 아직 없다.** `Notifier` 포트만 있고 Discord 웹훅 어댑터는 5단계에서 만든다. 그때까지 알림은 보내지지 않는다(보내지 못하면 기록하지 않으므로 어댑터가 생기면 다음 기회에 보내진다) |
| 3 | 호출 기록의 "하루"는 UTC 날짜라는 가정이다. 서버 쪽 집계의 기준 시각은 확인하지 못했다. 서버가 알려 주는 `used`가 실제 기준이라서 가정이 틀려도 서버 남은 수 점검이 보완한다 |
| 4 | 번역이 자연스러운지는 평가하지 않았다. 검증은 JSON 형식, 한자, 추론 문구 누출, 잘림, 빈 값만 본다. 벤치마크는 M3 |
| 5 | 429를 받으면 최대 30초 동안 작업이 멈춘다(`sleep`). 요약 잡이 겹쳐 실행되지 않게 하는 것은 7단계 잡 설정이 맡는다 |
| 6 | `Retry-After`가 날짜 형식이면 해석하지 않고 기본 5초를 기다린다 |
| 7 | 금지 문구 목록은 설계에서 "고급 설정에서 편집"으로 적었지만 아직 화면이 없다. 기본값(`We need to translate`, `Korean summary`)만 쓴다 |
| 8 | OTT 최종 판정(LLM 판정 + 키워드 확인)은 발송 단계에서 한다. 요약 단계는 LLM이 말한 값만 저장한다 |
| 9 | 모델 옵션 목록(`/models`)을 가져오는 요청이 하루 호출 한도에 포함되는지는 확인하지 못했다. 한 시간에 한 번이라 영향은 작다 |
| 10 | 스파이크 S2(Discord)는 아직 하지 않았다. 5단계 전에 필요하다 |
