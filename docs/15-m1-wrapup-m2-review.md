# 점검 기록: M1 마무리와 M2(구독 관리)

사용자 결정(2026-10-17): 수집과 발송이 정상 동작하므로 M1을 마무리하고 M2를 진행한다.

## 1. 결과 요약

| 항목 | 결과 |
|---|---|
| 테스트 | 2015개 통과(7단계 직후의 1736개 + CSRF 수정 32개 + M1 마무리 72개 + M2 175개), 약 45초 |
| 커버리지 | 줄 100%, 분기 100% |
| 린트/포맷, `mypy --strict`, `vulture` | 모두 통과 |
| BDD 연결 | **184개 중 184개**(연결하지 못한 것 없음). 이번에 SET-13, 14, TPC-12~14, FED-01~14를 연결했다 |
| 변이 확인 | M1 마무리 14개 + M2 17개, 모두 잡힘(처음에 M1 마무리에서 1개가 살아남아 보강했다) |
| 실제 크롬 확인 | M1 마무리 기능은 실제 어댑터로(가짜 웹훅과 가짜 키를 실제 Discord와 OpenRouter에 보냄), M2는 실제 공개 사이트(python.org)로 확인(§4) |

## 2. M1 마무리

| 기능 | 내용 |
|---|---|
| 웹훅 시험 전송(SET-13) | 설정 화면의 웹훅마다 "시험 전송". 선택한 웹훅으로 시험 메시지 한 건만 보내고, 실패하면 상태 코드와 이유를 보여 준다. 웹훅 주소는 화면에 나오지 않는다 |
| OpenRouter 키 확인(SET-14) | 키 정보(`GET /key`)만 조회한다. 채팅 호출을 하지 않아서 호출 한도와 오늘 호출 수를 쓰지 않는다. 유효, 거부(401, 403), 확인하지 못함(연결 실패, 5xx)을 구분한다 |
| 주제 판별 시험(TPC-12~14) | `/topics`에서 제목(과 본문)을 넣으면 실제 요약과 같은 프롬프트와 게이트웨이로 한 번 호출해서, 켜진 주제마다 LLM 선택, 키워드 일치, 최종 해당 여부, 보낼 웹훅을 보여 준다. 글이나 알림은 만들지 않는다. 5초 간격 제한, 입력 길이 제한. 모든 모델이 실패하면 키 거부, 잔액 부족, 요청 제한을 구분해서 알려 준다 |
| 조립 정리 | 실행기와 웹 화면이 같은 LLM 연결 코드(`build_llm_services`)를 쓴다 |

## 3. M2

| 구성 | 내용 |
|---|---|
| 개별 등록 | 주소를 확인하면 피드 주소는 제목을 보여 주고, 웹사이트 주소는 `<link rel="alternate">`로 알려 준 RSS와 Atom 피드를 최대 5개까지 실제로 가져와 확인한 뒤 후보로 보여 준다(상대 주소는 전체 주소로). 이미 구독 중이거나 가져오지 못하는 후보는 뺀다. 사설망 주소는 요청을 보내기 전에, 페이지가 알려 준 주소도 같은 규칙으로 거른다 |
| 등록 직전 재확인 | 화면에서 넘어온 값은 믿지 않는다. 등록할 때 서버가 다시 가져와서 피드인지 확인한다. 카테고리와 웹훅은 기존 상호 배제 규칙을 그대로 따른다 |
| 편집과 삭제 | 이름(200자), 머리말 이모지(8자), 점검 우선순위(보통, 매 슬롯), 최대 검사 항목 수(1~500, 비우면 기본값). 삭제는 확인란이 필요하고 글과 발송 기록이 함께 지워지지만 "이미 본 글" 기록은 남는다 |
| OPML 내보내기 | `/feeds/export.opml`. 카테고리는 폴더, 이름, 주소, 사이트 주소를 담고 웹훅은 담지 않는다. XML이 금지하는 문자는 지운다. 파일로 내려받고 캐시하지 않는다. 내보낸 파일을 다시 가져오면 전부 중복으로 나온다 |
| 수집기 | 결과에 피드 제목과 사이트 주소를 추가했고, 웹페이지 가져오기(1MB 제한, 같은 사설망 연결 검사)를 더했다 |

## 4. 실제 크롬으로 확인한 결과

| 확인 | 결과 |
|---|---|
| 웹훅 시험 전송 | 가짜 주소로 실제 Discord에 보내면 404가 오고, "웹훅 주소가 틀렸거나 삭제되었습니다(HTTP 404)"가 표시된다. 토큰과 주소는 화면에 없다 |
| 키 확인 | 가짜 키로 실제 OpenRouter에 조회하면 401이 오고, "키를 거부했습니다(HTTP 401)"가 표시된다. 키는 화면에 없다 |
| 주소 확인 | 사설망 주소는 사유와 함께 거절. 링크 없는 실제 웹페이지(example.com)는 "이 주소에서 피드를 찾지 못했습니다" |
| 자동 탐색 | python.org의 실제 피드 5개를 실제 제목과 함께 찾았다(PEP, 채용, PSF 소식, Python Insider, 릴리스) |
| 등록, 편집, 삭제 | 등록 후 안내 문구, 편집 값 유지, 확인 없이 삭제하면 거부, 확인하고 삭제하면 목록이 빔. 거부(403)된 요청 없음 |
| 내보내기와 다시 가져오기 | 실제 다운로드(`rss-hub-subscriptions.opml`)가 되고, 그 파일을 올리면 "신규 0 · 중복 1 · 오류 0" |

## 5. 이번 단계에서 발견하고 고친 것

| # | 내용 | 조치 |
|---|---|---|
| 1 | **변이가 1개 살아남았다**: 웹훅 시험 전송이 선택한 웹훅이 아니라 1번 웹훅으로 가도 테스트가 통과했다(시험이 항상 첫 번째 웹훅을 골랐다) | 두 번째 웹훅을 고르는 테스트로 변경 |
| 2 | 판별 시험에서 모든 모델이 실패했을 때 "응답하지 않았습니다"만 나와서, 가짜 키(401)의 진짜 원인이 안 보였다(실제 크롬 확인에서 발견) | 실패 종류별로 안내(키 거부, 잔액 부족, 요청 제한) |
| 3 | 내가 "서버가 피드 주소 길이를 제한하지 않는다"고 잘못 짐작했다. 확인해 보니 이미 2048자 제한이 있었다 | 코드는 그대로 두고, 느슨했던 테스트의 단언만 정확하게 바꿨다 |
| 4 | 시나리오 파일 공통 배경(주제 "OTT")을 새 시나리오의 단계 정의가 갖고 있지 않았다 | 배경 단계를 추가 |
| 5 | 일괄 치환 스크립트가 포맷터가 바꿔 놓은 줄바꿈 때문에 여러 번 중간에 멈췄다(일부 파일만 적용되는 일 포함) | 현재 모양을 확인하고 다시 적용 |
| 6 | 실제 크롬 확인 중 "다시 가져오기"가 실패한 것처럼 보였다. 서비스 오류가 아니라 브라우저가 내려받은 파일을 확장자 없는 임시 이름으로 저장해서 서비스가 "OPML 파일만 올릴 수 있음"으로 정상 거부한 것이다 | 화면 내용과 서버 응답을 직접 확인해서 원인을 구분하고, 확장자를 붙인 파일로 다시 확인 |

**과정에 대한 정직한 기록**: M1 마무리의 새 화면과 M2의 `/feeds` 화면, 내보내기는 구현을 먼저 쓰고 테스트를 나중에 썼다(실패를 먼저 확인하지 못했다). 변이 확인과 실제 크롬 확인으로 보완했다.

## 6. 점검 체크리스트

항상 포함: 단일 수행 원칙, 유지보수성, 확장성, 데드코드/미사용 변수·함수.

| 영역 | 점검 | 결과 |
|---|---|---|
| 단일 수행 원칙 | 계층 | 링크 찾기, 실패 설명, 편집 규칙, OPML 만들기는 순수 함수. 등록은 `FeedRegistrationService`가 맡고 수집기는 포트(`DiscoveryFetcher`)로만 안다 |
| 유지보수성 | 규칙의 위치 | 주소 규칙은 가져오기와 같은 `validate_feed_url` 하나를 쓴다. 사설망 차단도 같은 연결 검사를 쓴다 |
| 확장성 | 자동 탐색 | 지원 형식은 `FEED_TYPES` 한 곳. JSON Feed 같은 형식을 더하려면 해석기를 함께 더해야 해서 지금은 RSS와 Atom만 한다 |
| 데드코드 | 미사용 코드 | `vulture` 통과(`HTMLParser`가 호출하는 `handle_starttag`는 예외 목록) |
| 안정성 | 입력 | 깨진 HTML에서도 예외 없이 지금까지 찾은 것만 돌려준다. 페이지 1MB, 후보 5개, 주소 2048자 제한 |
| 보안 | 서버가 외부로 보내는 요청 | 사용자가 준 주소와 페이지가 알려 준 주소 모두 사설망이면 요청하지 않고, 실제 연결도 연결된 상대 IP를 검사한다. 오류 문구에 주소를 넣지 않는다 |
| 보안 | 화면 | 외부 사이트에서 온 제목, 주소는 이스케이프한다. 새 상태 변경 경로는 모두 교차 사이트 요청을 거부하고 브라우저의 같은 사이트 헤더를 받아들인다 |

## 7. 알려진 한계

| # | 내용 |
|---|---|
| 1 | **새 요약 프롬프트(주제 판별)가 실제 무료 모델에서 잘 동작하는지는 쓰시는 환경에서 `/topics`의 판별 시험으로 확인해야 한다.** 이 환경에서는 가짜 응답으로만 시험했다 |
| 2 | 자동 탐색은 `<link rel="alternate">`로 알려 준 RSS, Atom만 찾는다. `/feed`, `/rss.xml` 같은 흔한 경로를 추측해서 찾지는 않는다. 링크를 알려 주지 않는 사이트는 피드 주소를 직접 넣어야 한다 |
| 3 | 페이지의 `<base href>` 태그는 반영하지 않는다(리다이렉트를 거친 최종 주소를 기준으로 상대 주소를 푼다) |
| 4 | 로그인이 필요한 피드, 주소에 인증 정보가 있는 피드는 확인하지 않았다 |
| 5 | 이 환경은 TLS를 가로채는 프록시를 써서, 운영 코드의 연결 검사 세션으로 공개 HTTPS 사이트를 가져오려면 시험 스크립트에서 인증서를 지정해야 했다(운영 코드는 바꾸지 않았다). 쓰시는 가정용 환경에는 영향이 없다 |
| 6 | 구독 목록 화면은 검색, 정렬, 일괄 작업이 없다. 피드가 수백 개가 되면 한 페이지가 길어진다 |
| 7 | 삭제한 피드의 글은 복구할 수 없다(확인란으로만 보호) |
