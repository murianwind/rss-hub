# 5단계 점검 기록: 발송 서비스와 Discord 웹훅 어댑터

범위: 발송 기록 저장소(마이그레이션 4), Discord 웹훅 전송기와 시스템 알림 전송기(어댑터), 발송 서비스(라우팅, 메시지, 목적지별 기록과 재시도, 실패 처리), 상태 화면의 "서비스 주소 필요" 안내, 문단 선택 번역 기능의 제거.
이미 있던 도메인 규칙(`domain/routing`, `domain/message`, `domain/ott`)을 그대로 쓴다. 근거는 스파이크 S2 결과(`docs/09-spike-s2-result.md`).

## 1. 결과 요약

| 항목 | 결과 |
|---|---|
| 테스트 | 1138개 통과 (4단계의 996개 + 142개), 약 25초 |
| 커버리지 | 줄 100%, 분기 100% |
| 린트/포맷, `mypy --strict`, `vulture` | 모두 통과 |
| 변이 확인 | 구현을 일부러 망가뜨린 변이 25개 중 **1개가 처음에 살아남았다**(웹훅마다 따로 알리지 않는 변이). 테스트를 보강한 뒤 전부 잡힌다(§4) |
| BDD 연결 | 142개 중 **109개**(이전 90개 + 발송 19개). DLV 시나리오는 전부 연결 |
| 설치본 실제 실행 | 깨끗한 가상환경에 설치한 패키지로 **수집 → 요약 → 발송 전 과정**을 실제 requests, SQLite로 이어서 실행(§2) |

## 2. 설치본으로 끝까지 돌려 본 결과

피드 서버, OpenRouter, Discord는 로컬 가짜 서버였고, 나머지(어댑터, 서비스, 저장소)는 실제 코드다.

| # | 상황 | 결과 |
|---|---|---|
| 1 | 수집 | 오늘 발행된 새 글 1개가 `collected` |
| 2 | 요약 | 글이 채택되어 `ready`, LLM 호출 1번 |
| 3 | 발송, Discord가 503으로 응답 | 보낸 메시지 0, 글은 `ready`, 발송 기록은 `pending`, 시도 1회, 오류 `HTTP 503` |
| 4 | 발송, Discord 복구 | 메시지 1개 전송, 글은 `delivered`. 내용: 머리말(이모지, 사이트, 시각), 번역 제목, 요약, `🔗 [글 읽기](…/a/1)`. 멘션 차단(`allowed_mentions: {parse: []}`)과 `?wait=true`로 요청, 주소의 토큰은 출력하지 않음 |
| 5 | 다시 실행 | 보낸 것 0(중복 없음). Discord 요청은 모두 2번(실패 1, 성공 1) |

## 3. 만든 것

| 구성 | 내용 |
|---|---|
| `domain/delivery.py` | 응답 상태 코드를 다음 행동(보냄, 기다렸다 재시도, 영구 실패, 나중에 재시도)으로 가름, 한도 헤더로 미리 기다릴 시간, 429 대기 시간 |
| `storage/deliveries.py` | 글 하나를 목적지(웹훅과 용도)마다 따로 기록(마이그레이션 4). 시도 횟수, 마지막 오류, 메시지 id, 보낸 시각 |
| `adapters/discord_webhook.py` | 웹훅 전송기(`?wait=true`, 멘션 차단, 보내기 전 주소 검사, 실패를 결과로 반환), 시스템 알림 전송기 |
| `services/deliver.py` | 발송 서비스 |
| 저장소 보강 | 글을 `delivered`로 바꾸고 "이미 본 글" 기록에 표시, 카테고리의 웹훅 조회 |
| 상태 화면 | 서비스 주소가 없어서 발송을 기다리는 글이 있으면 "서비스 주소 필요" 안내 |

## 4. 이번 단계에서 발견하고 고친 것

| # | 내용 | 조치 |
|---|---|---|
| 1 | **변이 확인에서 살아남은 것**: 영구 실패 알림을 웹훅마다 구분하는 코드를 지워도 테스트가 통과했다. 웹훅 두 개가 각각 죽었을 때 한쪽 알림이 쿨다운에 묻힐 수 있는 결함이었다 | 웹훅 두 개가 따로 알림을 받는 테스트 추가 |
| 2 | DLV-15 시나리오에 "ready인 글이 있다"는 단계가 빠져 있었다(글 없이 발송 보류를 검증할 수 없다) | 시나리오 수정 |
| 3 | 이전 시나리오 연결에서 쓴 스텝 패턴이 겹쳤다. `피드의 웹훅 지정은 {값}이다`가 "…이고 카테고리의 웹훅 지정은 …이다" 문장까지 삼켜서 DLV-01이 실패했다 | 공백 없는 값만 받는 패턴으로 좁힘 |
| 4 | 테스트 환경의 웹훅 주소에 한글이 들어가서(웹훅 이름을 토큰에 넣었다) 주소 검증을 통과하지 못했다 | 숫자 토큰으로 수정 |
| 5 | 변이 확인 명령이 시간 제한(300초)에 걸려 **중간에 끊겼다.** 끊긴 시점에 소스가 망가진 채 남았을 수 있어서 바로 확인했다(테스트 통과, 변이 흔적 검사, 백업과 비교). 이상 없었다. 이어서 백그라운드로 돌렸지만 **명령이 끝나면 프로세스가 함께 죽어서** 실제로는 실행되지 않았다 | 소스를 백업하고 3구간으로 나눠서 시간 제한 안에서 실행했고, 매번 백업과 비교해서 복구를 확인했다 |
| 6 | 테스트 도우미에 쓰이지 않는 함수가 하나 남았다 | `vulture`가 찾아서 삭제 |
| 7 | 가짜 서버가 클라이언트가 먼저 끊은 경우 오류 로그를 길게 찍었다(시간 초과 시험) | 가짜 서버에서 끊김 예외를 무시 |

## 5. 점검 체크리스트

항상 포함: 단일 수행 원칙, 유지보수성, 확장성, 데드코드/미사용 변수·함수.

| 영역 | 점검 | 결과 |
|---|---|---|
| 단일 수행 원칙 | 계층 | 응답 해석과 속도 조절은 순수 함수(`domain/delivery`), HTTP는 어댑터, 기록은 저장소, 흐름은 서비스가 맡는다. 서비스는 `WebhookSender` 포트만 알고 `requests`를 모른다 |
| 단일 수행 원칙 | 큰 함수 | `DeliveryService._send_one`이 429 재시도, 영구/일시 실패 분기를 한 함수에서 처리한다. 결과를 네 가지로 가르는 한 가지 일이라 유지한다 |
| 유지보수성 | 설정 | 서비스 주소, 기본/OTT/시스템 웹훅은 매번 설정에서 읽는다(DLV-20, 재시작 없이 반영) |
| 확장성 | 알림 경로 | 시스템 알림은 `Notifier` 포트로 분리했고, 이번에 Discord 전송기를 구현했다. 다른 채널로 바꿔도 알림 서비스는 그대로다 |
| 데드코드 | 미사용 코드 | `vulture` 통과 |
| 안정성 | 목적지별 기록 | 모든 목적지로 보냈을 때만 `delivered`. 한쪽만 실패하면 실패한 곳만 다시 보낸다(기존 코드는 한쪽만 성공해도 완료로 처리했다, DLV-11) |
| 안정성 | 중복 발송 | 목적지 기록이 (글, 웹훅, 용도)로 유일하다. 이미 보냈거나 영구 실패한 목적지는 다시 보내지 않는다 |
| 안정성 | 장애 | Discord가 내려가면 3번 연속 실패에서 이번 실행을 멈춘다. 한 실행에 최대 25개. 429는 한 번 기다렸다 재시도하고, 또 실패하면 멈춘다 |
| 안정성 | 속도 | 한도 헤더의 남은 횟수가 0이면 미리 기다려서 429를 피한다 |
| 보안 | 비밀 값 | 웹훅 주소(토큰)는 기록, 로그, 알림 문구, 오류 문구에 넣지 않는다. 전송기가 주소를 담은 예외를 올려도 종류 이름만 남긴다(DLV-17 시나리오로 로그, 응답, 오류 기록을 검사) |
| 보안 | 멘션 | 글 제목이나 요약의 `@everyone` 같은 문구가 알림이 되지 않도록 `allowed_mentions`를 비운다 |
| 보안 | 주소 | 보내기 직전에 Discord 주소인지 한 번 더 확인한다(설정 화면 검증에 더한 방어) |

## 6. 설계 결정(확인이 필요하면 알려 주세요)

| # | 결정 |
|---|---|
| 1 | 웹훅이 영구 실패하면 글은 `ready`로 남고 그 대상으로는 다시 보내지 않는다. 사용자가 기본 웹훅 등을 **다른 웹훅으로 바꾸면** 대기 중이던 글이 새 웹훅으로 나간다. 죽은 웹훅이 길게 방치되면 `ready` 글이 쌓인다(알림이 계속 간다) |
| 2 | 400 같은 4xx(408, 429 제외)도 영구 실패로 본다(다시 보내도 소용없으므로). S2에서 400의 본문을 읽지 못해서 이유는 알 수 없다 |
| 3 | 한 실행에 최대 25개를 보낸다. 요약 주기가 60초면 시간당 1500개까지 나갈 수 있다 |
| 4 | OTT 최종 판정(LLM 맞음 + 키워드 + 피드 설정)은 발송 직전에 한다. 키워드 목록은 기본값만 쓴다(설정 화면은 아직 없다) |

## 7. 알려진 한계

| # | 내용 |
|---|---|
| 1 | **발송 서비스도 아직 주기적으로 실행되지 않는다.** 그래서 지금 올린 이미지는 Discord에 아무것도 보내지 않는다. 수집, 요약, 발송을 잡으로 연결하는 것은 7단계다 |
| 2 | **429 응답의 모양을 확인하지 못했다**(S2에서 연속 발송이 한도에 걸리지 않았다). `Retry-After` 헤더, 본문의 `retry_after`를 읽는 부분은 문서 기준의 가정이다. 실제로 429를 받으면 확인이 필요하다. 한도 헤더로 미리 기다리기 때문에 429를 받을 일은 적을 것이다 |
| 3 | 삭제된 웹훅(404)과 400의 응답 본문을 확인하지 못했다. 상태 코드만으로 판단한다 |
| 4 | 글에 링크 미리보기(embed)를 끄지 않았다. Discord가 서비스 글 주소의 미리보기를 만들 수 있다 |
| 5 | 보낸 메시지를 나중에 고치거나 지우는 기능은 없다(주소를 바꿔도 이미 나간 메시지는 그대로다, DLV-20) |
| 6 | 기본 웹훅이 없을 때의 알림과 영구 실패 알림은 **시스템 웹훅이 지정되어 있어야** 간다. 시스템 웹훅이 없으면 알림 없이 멈춘다(기록하지 않으므로 지정하면 다음에 간다) |
| 7 | 첫 메시지의 모양(굵은 글씨, 링크)을 사람이 눈으로 확인한 결과는 받지 못했다 |
| 8 | OTT 키워드 목록과 금지 문구 목록을 편집하는 화면이 없다 |
