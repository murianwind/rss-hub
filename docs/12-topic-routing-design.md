# 주제 알림과 웹훅 구조 설계 (M1 반영)

사용자 결정(2026-10-16): ① 주제 판별은 "LLM 확인 + 키워드 보완" ② 주제 알림을 M1에 넣는다. ③ (처음에는 피드별 웹훅을 없애기로 했으나 2026-10-17에 **복구**했다. 아래 §7이 현재 규칙이다.)

## 1. 웹훅 구조

| 단계 | 규칙 |
|---|---|
| 기본 웹훅 | 등록한 모든 피드의 알림이 간다 |
| 카테고리 웹훅 | 사용자가 피드를 모아 만든 카테고리에 웹훅을 지정하면 그 카테고리의 피드 알림은 그 웹훅으로 간다. 지정하지 않으면 기본 웹훅 |
| 주제 웹훅 | 글이 어떤 주제에 해당하면, 위의 대상에 더해 그 주제의 웹훅으로도 한 번 더 간다 |
| 시스템 웹훅 | 서비스 상태 알림(호출 상한, 잔액 부족 등) |

- **사라지는 것**: OTT 전용 웹훅 역할, 피드별 "OTT 판정" 켜고 끄기. (피드별 웹훅 지정은 §7에서 카테고리에 속하지 않은 피드에 한해 복구했다. 쓰지 않는 DB 열은 SQLite가 외래 키가 걸린 열을 지울 수 없어서 남겨 둔다.)
- 같은 웹훅이 여러 대상에 걸리면 **메시지는 한 번만** 간다(예: 기본 웹훅이 주제 웹훅과 같을 때, 두 주제가 같은 웹훅일 때).
- 기본 대상(카테고리 웹훅 또는 기본 웹훅)을 정할 수 없으면 주제 웹훅이 있어도 발송을 보류하고 시스템 알림을 보낸다(기존 규칙 유지).

## 2. 주제

주제 하나 = 이름 + 한 줄 설명 + 키워드 목록 + 웹훅(선택) + 켜짐/꺼짐.

### 2.1 판별 규칙 ("LLM 확인 + 키워드 보완")

글이 주제에 해당하려면 **둘 다** 만족해야 한다.
1. 요약할 때 LLM이 그 주제 번호를 골랐다.
2. 제목이나 본문(HTML 제거 후)에 그 주제의 키워드가 하나라도 있다.

- 키워드를 하나도 등록하지 않은 주제는 LLM의 판단만으로 정한다.
- 꺼진 주제는 LLM에게 묻지도 않고, 판별하지도 않는다.
- 한글 키워드는 부분 문자열, 영문 키워드는 단어 단위로 대소문자 구분 없이 일치한다(기존 OTT 규칙 그대로. `disney+`처럼 기호로 끝나는 키워드, `ott`가 `bottle` 안에서 일치하지 않는 것 포함).
- **해석 메모**: "키워드 보완"을 "LLM이 놓친 글을 키워드가 건져 준다(OR)"가 아니라 "LLM의 환각을 키워드가 걸러 준다(AND)"로 해석했다(기존 OTT와 같은 방식). OR이 의도였다면 알려 주시면 한 곳(`domain/topics.py`의 `match_topic`)만 바꾼다.

### 2.2 입력 규칙

| 항목 | 규칙 |
|---|---|
| 이름 | 1~40자, 다른 주제와 중복 불가(대소문자 구분 없이) |
| 설명 | 200자까지. LLM에게 주제를 설명하는 글이라 비워 두면 이름만 전달된다 |
| 키워드 | 쉼표나 줄바꿈으로 구분, 앞뒤 공백 제거, 대소문자 구분 없이 중복 제거, 항목당 40자, 최대 100개 |
| 개수 | 주제는 20개까지(요청 프롬프트 길이를 제한한다) |

### 2.3 처음 설치할 때

주제가 하나도 없고 한 번도 만든 적이 없으면 **"OTT"** 주제를 만든다. 설명은 "OTT, 스트리밍 콘텐츠(영화, 드라마, TV 쇼, 스트리밍 서비스 소식)", 키워드는 기존 OTT 키워드 목록, 웹훅은 이전 설정의 OTT 웹훅이 있으면 그것. 사용자가 지워도 다시 만들지 않는다.

## 3. 요약 요청(LLM 계약) 변경

- (§8로 대체) 후보 주제(키워드가 맞았거나 키워드가 없는 주제)가 있으면 프롬프트에 번호와 설명을 넣고, 응답에 `"topics": [번호, ...]`를 요구한다. 후보가 없으면 이 항목을 요청하지 않는다.
- 응답 검증: `topics`가 없거나 목록이 아니면 "해당 없음"으로 보고 요약은 채택한다(기존 `is_ott` 누락 규칙과 같다). 목록 안에서 **알 수 없는 번호, 문자열이 아닌 숫자 형식이 아닌 값, 참/거짓은 무시**한다. `"1"` 같은 숫자 문자열은 받는다.
- 글에는 LLM이 고른 번호를 기록한다(`articles.llm_topics`). `is_ott` 열은 쓰지 않는다.
- 호출 횟수는 그대로다(한 번에 모든 주제를 판별한다). 주제 하나당 프롬프트가 약 30~60토큰 늘어난다.

## 4. 발송과 기록

발송 직전에 켜진 주제를 읽어서 각 주제를 판별하고, 해당한 주제는 `article_topics(article_id, topic_id, matched_keywords)`에 기록한다(M5의 피드백과 키워드 개선 제안에 쓴다). 목적지는 기본 대상 하나와 해당 주제들의 서로 다른 웹훅이다. 발송 기록의 용도(`purpose`)는 `primary` 또는 `topic:<번호>`다.

## 5. 화면

| 화면 | 내용 |
|---|---|
| `/topics` | 주제 목록, 추가, 수정(이름, 설명, 키워드, 웹훅, 켜짐), 삭제 |
| `/categories` | 카테고리 목록(피드 수), 카테고리별 웹훅 지정과 해제, 카테고리 추가. 피드를 카테고리에 넣는 화면은 M2(구독 목록). OPML 폴더로 가져온 카테고리는 바로 보인다 |
| 설정 | 웹훅 역할은 **기본, 시스템** 두 가지 |
| 가져오기 | 가져오기 화면에는 피드별 웹훅 선택이 없다(피드 화면 `/feeds`에서 지정한다). Gizmodo 프리셋은 우선순위, 최대 검사 수, 이모지만 바꾼다 |

## 6. 지금 하지 않는 것

- 주제의 적용 범위(특정 카테고리의 피드에만 적용). 지금은 모든 피드에 적용한다. 필요하면 M2.
- 좋아요/싫어요와 키워드 개선 제안(M5). 이번에는 `article_topics`에 기록만 해 둔다.
- 주제 순서 바꾸기, 주제별 이모지나 머리말.

## 7. 현재 규칙(2026-10-17): 피드 웹훅 복구와 "기본에서 빠짐"

사용자 결정으로 §1을 아래처럼 바꿨다.

| 단계 | 규칙 |
|---|---|
| 기본 웹훅 | 피드 웹훅도 카테고리 웹훅도 없는 피드의 알림이 간다 |
| 피드 웹훅 | 카테고리에 **속하지 않은** 피드에 지정할 수 있다. 지정하면 그 피드 알림은 그 웹훅으로만 가고 기본 웹훅에서는 빠진다 |
| 카테고리 웹훅 | 지정하면 그 카테고리 피드의 알림은 그 웹훅으로만 가고 기본 웹훅에서는 빠진다 |
| 주제 웹훅 | 위 대상에 **더해** 주제 웹훅으로도 간다. 피드나 카테고리 웹훅으로 가는 피드의 주제 글도 **기본 웹훅으로는 가지 않는다**(사용자가 정한 B안) |

- 결정 순서는 피드 웹훅 → 카테고리 웹훅 → 기본 웹훅이다. 같은 웹훅은 한 번만 보낸다.
- **상호 배제**: 카테고리에 속한 피드에는 피드 웹훅을 지정할 수 없고, 웹훅이 지정된 피드는 카테고리에 넣을 수 없다(먼저 웹훅 지정을 해제해야 한다). 카테고리에서 빼면 피드 웹훅을 다시 지정할 수 있다. 저장소가 규칙을 지키고, 어겨도 데이터가 깨지지 않는다.
- 피드 웹훅이 있으면 기본 웹훅이 없어도 그 피드는 발송된다. 기본 웹훅이 필요한 피드가 있는데 지정되어 있지 않으면 발송을 보류하고 시스템 알림을 보낸다(DLV-15).
- 화면: `/feeds`(피드별 카테고리와 웹훅 지정), `/categories`, `/topics`.
- 시나리오: DLV-01, 23, 24, TOP-10~14.

## 8. 현재 규칙(2026-10-20): 키워드 먼저, LLM은 후보만 확인

판정 공식(`키워드 AND LLM`)은 그대로이고, **LLM에게 묻는 방식**을 바꿨다.

| | 이전 | 지금 |
|---|---|---|
| 요약 요청에 넣는 주제 | 켜진 주제 전부 | **키워드가 맞은 주제와 키워드가 없는 주제**(후보)만 |
| 후보가 없을 때 | 주제 항목을 요청해서 답을 버렸다 | 주제 항목 자체를 요청하지 않는다 |
| LLM이 후보가 아닌 주제를 고르면 | 키워드가 걸러 냈다 | 응답 검증이 유효 번호를 후보로 제한해서 무시한다 |
| 호출 수 | 글당 1회 | 글당 1회(변화 없음) |
| 요청 크기 | 글당 약 250토큰(주제 하나당 약 20토큰 증가) | 키워드가 안 맞는 글은 약 150토큰 |

- 근거는 측정으로 확인한 요청 크기 감소와 환각 차단이다. 정확도 향상은 측정하지 못했고, 운영에서 `/topics`의 판별 시험으로 확인한다.
- **대가**: LLM이 키워드 없이 고른 주제(키워드가 놓친 글의 신호)가 사라진다. M5의 키워드 개선 제안은 사용자가 "주제로" 버튼을 누른 글에서 얻는다.
- 키워드가 없는 주제는 항상 후보이므로 기존처럼 LLM만으로 정한다.
- 요약 직후에 주제 소속(`article_topics`)을 기록해서 뷰어의 주제별 목록이 알림 전달과 무관하게 동작한다.
- 시나리오: SUM-15, 16, 18~20, TPC-12~15.

## 9. 사용자 피드백(M5, 2026-10-20)

LLM을 학습시키는 것이 아니라, 판정을 즉시 바로잡고 키워드와 요청의 예시를 고치는 방식이다.

| 동작 | 결과 |
|---|---|
| 싫어요 | 그 주제 목록에서만 글을 뺀다(`rejected=1`). RSS, 카테고리 목록에는 남고 되돌릴 수 있다. 아직 보내지 않은 글은 그 주제 웹훅으로 가지 않는다 |
| 주제로 | 글을 그 주제에 넣는다(`source=manual`). 키워드와 LLM 판정과 상관없다. 아직 보내지 않은 글은 주제 웹훅으로 간다. **이미 보낸 알림은 다시 보내지 않는다** |
| 자동 판정이 다시 기록될 때 | 키워드만 갱신하고 사용자가 정한 `source`, `rejected`는 그대로 둔다 |
| 키워드 개선 제안 | "주제로" 글의 제목에 공통으로 나오는 단어(2개 이상)를 추가 제안, 싫어요 비율이 높은 키워드(2개 이상, 절반 이상)를 제거 제안. **승인해야만** 반영, 마지막 키워드는 지울 수 없다 |
| 요청의 예시 | 설정 `topic_feedback_examples`(0~5, 기본 0): 후보 주제마다 "주제로"로 넣은 글 제목과 싫어요로 뺀 글 제목을 요청에 넣는다. 효과는 측정하지 못해서 기본은 꺼 두었다 |

- 키워드 먼저 방식(§8)은 LLM이 키워드 없이 고른 주제라는 누락 신호를 없앴다. 그 신호는 "주제로" 버튼이 대신한다.
- 돌아갈 곳(`next`)은 이 서비스의 읽기 화면 경로만 허용한다(열린 리다이렉트 방지).
- 시나리오: FBK-01~12.
