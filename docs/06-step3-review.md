# 3단계 점검 기록: 피드와 글 저장소, 수집 서비스

범위: 피드, 글, "이미 본 글" 저장소(마이그레이션 2), 수집 서비스(슬롯 실행, 점검, 기준선, 오류 격리, 스케줄 재사용), HTTP 피드 수집기(requests + feedparser), 활동 측정과 항목 필드 추출 규칙.
진행 순서: 테스트 작성 → **실패(red) 확인** → 구현 → 통과(green) → 점검.

## 1. 결과 요약

| 항목 | 결과 |
|---|---|
| 테스트 | 717개 통과 (2단계의 588개 + 129개), 약 6초 |
| 커버리지 | 줄 100%, 분기 100% |
| 린트/포맷, `mypy --strict`, `vulture` | 모두 통과 |
| 변이 확인 | 구현을 일부러 망가뜨린 변이 15개를 **모두** 테스트가 잡음(생존 0) |
| BDD 연결 | 139개 중 **59개**(이전 33개 + 수집 24개 + 스케줄 재사용 2개). 수집 시나리오(COL)는 전부 연결 |
| 설치본 실제 실행 | 깨끗한 가상환경에 설치한 패키지로 **실제 feedparser, requests, SQLite, 로컬 피드 서버**를 써서 5단계를 확인 (아래 §2) |

## 3. 만든 것

| 구성 | 내용 |
|---|---|
| `domain/activity.py` | 최근 7일 글 수, 오늘 글 수, 가장 최근 발행 시각을 센다(7일 창은 정확히 7일 전을 포함) |
| `domain/entries.py` | 피드 항목에서 제목, 링크, 본문 HTML 원본(summary → description), 발행 시각 원문을 뽑는다 |
| `storage/` | 마이그레이션 2(카테고리, 피드, 통계, 본 글, 글), `FeedRepository`, `ArticleRepository` |
| `services/collect.py` | `run_slot()`(스케줄과 슬롯), `collect_feeds()`(점검), 스케줄 재사용 |
| `services/ports.py` | `FeedFetcher` 포트, `FetchResult`, `FetchError` |
| `adapters/http_feed_fetcher.py` | 조건부 요청, 크기 제한(5MB), 피드가 아닌 응답 거부, 리다이렉트, 시간 제한 |

## 4. 점검 체크리스트

항상 포함: 단일 수행 원칙, 유지보수성, 확장성, 데드코드/미사용 변수·함수.

| 영역 | 점검 | 결과 |
|---|---|---|
| 단일 수행 원칙 | 수집 서비스 | 스케줄 선택(`run_slot`), 점검 반복(`collect_feeds`), 피드 하나 점검(`_check`), 오늘 글 저장(`_store_todays_articles`)으로 나눴다. 날짜 해석, GUID, 활동 측정, 필드 추출은 모두 도메인 함수를 쓴다 |
| 단일 수행 원칙 | 저장소 | `FeedRepository`는 피드와 통계, `ArticleRepository`는 글과 "본 글" 기록만 다룬다. 둘 다 SQL만 알고 규칙은 모른다 |
| 유지보수성 | 설정 | 점검 한도, 시간대, 수집 주기, 배치 크기는 모두 설정에서 읽는다(매번 읽어서 재시작 없이 반영) |
| 확장성 | 수집기 교체 | `FeedFetcher` 포트 뒤에 두어서 테스트는 가짜, 운영은 requests 어댑터를 쓴다. 다른 방식(예: 비동기)으로 바꿔도 서비스는 그대로다 |
| 데드코드 | 미사용 코드 | `vulture` 통과. 프레임워크가 호출하는 이름(`do_GET` 등)만 예외로 둠 |
| 안정성 | 오류 격리 | 피드 하나의 `FetchError`와 예상 못한 예외(`ValueError` 등)를 모두 기록하고 나머지를 계속한다(테스트). 예상 못한 예외는 `logging.exception`으로 남기고 피드 주소는 로그에 넣지 않는다(주소에 토큰이 있을 수 있다) |
| 안정성 | 중복 | 중복 판단은 `seen_guids` 하나다. 글 저장과 "본 글" 기록이 한 트랜잭션이라 중간에 실패해도 어긋나지 않는다. 피드를 지워도 "본 글" 기록은 남아서 다시 등록해도 옛 글이 되살아나지 않는다(테스트) |
| 안정성 | 외부 입력 | 응답 크기를 5MB로 제한하고, 읽는 중에 넘으면 중단한다. 피드가 아닌 응답은 실패로 기록한다 |
| 시간/인코딩 | 시간대 | "오늘"과 슬롯의 분은 서비스 시간대로 계산한다. 프로세스(컨테이너) 시간대를 UTC로 바꿔도 결과가 같음을 시나리오(COL-07)로 확인했다. 시간은 UTC로 저장한다 |
| 보안 | 피드 주소 | 로그에 주소를 남기지 않는다. 서버가 임의 주소를 가져오는 것(SSRF)은 §6 한계 참고 |

## 5. 이번 단계에서 발견하고 고친 것

| # | 내용 | 조치 |
|---|---|---|
| 1 | **기존 코드는 HTML 페이지 같은 응답을 "글이 0개인 피드"로 보고 영원히 성공으로 처리**한다. 피드 주소가 잘못되어도 알 수 없다 | 새 구현은 `NotAFeed`로 실패 기록. 시나리오 COL-23, 설계 §12 #15 |
| 2 | 스케줄 재사용 판단이 "기본 배치 크기"를 보지 않아서, 설정에서 값을 바꿔도 다음 시간까지 반영되지 않았다 | `schedule_fingerprint`에 기본 배치 크기를 넣었다(테스트 추가) |
| 3 | 응답 크기 제한이 없으면 아주 큰 응답이 메모리를 쓸 수 있다 | 5MB 제한과 시나리오 COL-24 추가 |
| 4 | 느린 서버 테스트가 종료 시 지연 응답을 기다려서 전체가 16초 걸렸다 | 테스트 서버를 데몬 스레드와 짧은 폴링으로 바꿔서 6초로 줄였다 |
| 5 | BDD에서 모든 `When` 문장에 일치하는 단계 패턴을 만들 뻔했다 | 알려진 7개 변경 문구만 일치하는 패턴으로 제한했다. 안 그랬으면 다른 단계와 충돌했을 것이다 |

## 6. 스택과 설계 변경

| # | 내용 |
|---|---|
| 1 | HTTP 클라이언트는 설계에 적었던 `httpx` 대신 **`requests`**를 쓴다. 기존 스크립트도 requests였고 feedparser와 함께 가장 널리 검증된 조합이며, 동기 호출이라 지금 구조에 맞다. (`httpx`는 테스트의 `TestClient`용으로 `httpx2`만 쓴다) |
| 2 | `requests`와 `feedparser`는 타입 정보가 없어서 `mypy`가 이 두 모듈만 예외로 둔다 |

## 7. 알려진 한계

| # | 내용 |
|---|---|
| 1 | **수집 서비스는 아직 주기적으로 실행되지 않는다.** 잡 연결(겹침 방지 SCH-12, 중단 후 재개 SCH-13 포함)은 7단계 |
| 2 | 한 슬롯의 피드를 **순차로** 가져온다. 피드 15개가 모두 최대 시간(연결 4초 + 읽기 12초)까지 걸리면 4분이 넘을 수 있다. 수집 주기 5분 안에서는 버티지만 여유가 작다. 실제 소요 시간을 보고 병렬 처리를 결정한다 |
| 3 | 스케줄은 메모리에 보관한다. 재시작하면 다시 만든다(비용이 작다) |
| 4 | **서버가 임의의 피드 주소를 가져오므로**, 설정 화면이 인증 없이 열려 있으면 내부망 주소(예: `http://192.168.0.1/`)를 피드로 등록해서 서버가 내부 서비스에 요청을 보내게 만들 수 있다. 피드 등록 화면이 생기는 6단계(가져오기)와 M2에서 사설망 주소 허용 정책을 정한다 |
| 5 | `requests`는 환경 변수의 프록시 설정(`HTTP_PROXY` 등)을 따른다. 이 프로젝트는 환경 변수 설정을 쓰지 않는 방침이라, 필요하면 명시적으로 끄는 것을 검토한다 |
| 6 | 피드를 지우면 그 피드의 글도 함께 지워진다(발송 이력도 마찬가지). 구독 삭제 화면(M2)에서 확인 단계를 둔다 |
| 7 | 스파이크 S1, S2는 아직 하지 않았다. 4단계(요약), 5단계(발송) 전에는 필요하다 |
